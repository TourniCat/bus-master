# Bus Master — Product Vision

> Status: Pre-production / Planning
> Working title: **Bus Master**
> Last updated: 2026-08-27

## 1. High Concept

**실제 지구상의 원하는 지역을 선택하고, 그 지역의 실제 도로·건물 배치를 기반으로 생성된 귀여운 로우폴리 미니어처 도시에서 자신만의 버스망을 만들고 운영하는 게임.**

핵심 판타지는 다음과 같다.

> **내가 아는 그 길 위에, 내가 원하는 버스망을 만든다.**

현실을 1:1 복제하는 교통 시뮬레이터가 아니라, 실제 지도는 도시의 **뼈대**로 사용하고 승객 수요·교통량·경제·성장은 게임성을 위해 절차적으로 재해석한다.

---

## 2. 현재까지 확정된 방향

### 2.1 실제 지역을 게임판으로 사용

- 플레이어가 세계 지도에서 원하는 지역을 선택한다.
- 실제 도로망, 건물 footprint, 주요 POI 등을 지도 데이터에서 가져온다.
- 선택한 영역을 게임 플레이가 가능한 미니어처 도시로 변환한다.
- 지도 데이터 후보의 중심은 OpenStreetMap 계열이다.

### 2.2 아트 방향

- **Kenney풍의 귀엽고 코지한 Low-poly 3D**를 기본 아트 방향으로 한다.
- 실제 건물 외관을 정확하게 복원하는 것이 목표가 아니다.
- 일반 건물은 지도상의 위치·크기·용도·높이 등의 데이터를 이용해 절차적으로 표현한다.
- 랜드마크 역시 실제 형태를 일일이 재현하지 않고 카테고리별 범용 모델을 사용한다.
  - 동상 → 범용 동상
  - 교회 → 범용 종교시설
  - 경기장 → 범용 경기장
  - 박물관 → 범용 문화시설
  - 관광명소 → 눈에 띄는 범용 랜드마크
- 공원·호수·강 등은 가능한 경우 실제 영역 형태를 활용한다.

### 2.3 핵심 플레이는 버스 노선

- 도시 건설 자체가 핵심이 아니다.
- 복잡한 버스 회사 경영 시뮬레이션도 핵심이 아니다.
- 핵심 행동은 다음과 같다.
  1. 정류장 배치/선택
  2. 버스 노선 설계
  3. 차량 배치 및 증차
  4. 승객 흐름과 혼잡 관찰
  5. 문제가 생긴 구간의 노선 재설계
  6. 도시의 대중교통 품질 개선

### 2.4 지도 데이터 오류를 플레이어가 수정 가능

실제 지도 데이터는 완벽하지 않다는 것을 전제로 한다.

- 건물 용도 수정
- POI 종류 수정
- 필요시 일부 도로 속성 수정
- 수정 내용은 원본 지도 데이터와 분리된 override 형태로 저장

장기적으로는 Steam Workshop 등에서 지역 보정 데이터를 공유하는 구조를 고려한다.

### 2.5 커뮤니티 데이터는 공식 데이터와 분리

예상 구조:

`Base Map Data -> Game Interpretation -> Local/User Override -> Community/Workshop Override`

커뮤니티가 만든 데이터가 마음에 들지 않으면 제거하면 원본 상태로 돌아올 수 있어야 한다.

## 3. 현재 가장 유력한 제품 방향 — 아직 최종 확정 아님

최근 논의에서는 단발성 퍼즐보다는 다음 구조가 더 적합할 가능성이 높다고 보고 있다.

### Cozy Transit Management + Route Optimization

- 자기 동네를 한 번 선택하고 계속 가지고 논다.
- 버스망이 지속적으로 성장한다.
- 게임을 꺼도 제한적인 오프라인 진행이 가능하다.
- 플레이어가 돌아오면 누적된 운영 결과와 새로운 병목을 확인한다.
- 방치는 **성장/운영 결과**를 만들고, 직접 플레이는 **노선 문제 해결**에 집중한다.

예시:

`노선 설계 -> 운행 -> 승객/수익/문제 발생 -> 업그레이드 -> 노선 최적화 -> 도시 확장`

이 방향은 모바일과 특히 잘 맞지만, 아직 플랫폼 및 게임 모드 구조는 확정하지 않는다.

## 4. 현재 제품 원칙

### 4.1 실제성보다 알아볼 수 있음

플레이어가 원하는 것은 건물 외벽 색깔까지 정확한 디지털 트윈이 아니라 **"여기 내가 아는 동네다"**라는 인식이다.

우선순위:

1. 도로망과 교차로
2. 강·호수·공원·철도 같은 큰 지형 요소
3. 주요 POI와 실제 이름
4. 건물 위치와 대략적인 크기
5. 건물 용도
6. 실제 건물 외형 — 낮은 우선순위

### 4.2 복잡한 시뮬레이션보다 읽기 쉬운 결과

- 모든 주민을 개별 NPC로 시뮬레이션할 필요 없음
- 모든 자동차를 개별 물리 객체로 돌릴 필요 없음
- 수요와 교통량은 구역/도로 단위의 수치 모델을 우선
- 화면에는 이해에 필요한 수준의 차량과 사람만 시각적으로 표현

### 4.3 플레이어는 교통 관리자이지 시장이나 버스회사 CEO가 아님

초기 핵심 범위에서는 다음과 같은 요소를 지양한다.

- 직원 급여/휴가/채용 관리
- 차량 부품 단위 정비
- 보험
- 대출
- 세차
- 회계 시뮬레이션
- 건물 하나씩 직접 건설

이런 요소가 노선 최적화를 더 재미있게 만들지 않는다면 추가하지 않는다.

### 4.4 지도 생성 기술보다 게임성이 먼저

전 세계 자동 지도 생성은 강력한 마케팅 훅이지만, **노선을 만들고 개선하는 행위 자체가 재미있지 않으면 의미가 없다.**

따라서 첫 프로토타입은 실제 지도 연동 없이도 핵심 루프를 검증할 수 있어야 한다.

## 5. 미정 사항 — 기획 단계에서 순서대로 결정할 것

### A. 게임 정체성

- 코지 장기 운영 게임인가?
- 퍼즐 챌린지 게임인가?
- 두 모드를 병행하는가?
- 실패/게임오버가 존재하는가?

### B. 플랫폼

- Mobile-first인가?
- Steam-first인가?
- 한 코드베이스로 PC/Mobile 동시 설계인가?

### C. 세션 구조

- 2~5분 짧은 체크인 중심인가?
- 10~30분 적극적 플레이 중심인가?
- 오프라인 진행은 어느 정도인가?

### D. 경제와 성장

- 수익의 역할
- 버스 구매/증차 방식
- 노선/정류장 비용
- 도시 확장 방법
- 업그레이드 트리 존재 여부

### E. 승객과 수요

- 주거/업무/교육/상업/관광 수요
- 시간대별 출퇴근
- 환승
- 대기시간
- 목적지 선택 방식
- 대중교통 선호도 및 자동차 의존도

### F. 도로 교통

- 도로 혼잡 모델
- 버스 지연
- 버스 bunching
- 버스전용차로
- 일반 차량과 버스의 상호작용 정도

### G. 실제 지도 범위

- 플레이 영역의 물리 크기
- 다운로드/캐싱 방식
- OSM 및 추가 데이터 소스
- 건물 높이 및 용도 추론
- 자연 지형 처리

### H. 지도 보정 / 모딩

- 플레이어 보정 UI
- override 데이터 포맷
- Steam Workshop 지원 시점
- 지역 보정팩과 시나리오팩 분리 여부

### I. 수익 모델

아직 미정.

후보:

- PC 일회성 구매
- 모바일 유료
- 모바일 무료 + Full Game Unlock
- 무료 + 코스메틱/확장 콘텐츠

강제 전면 광고 중심 구조는 현재 게임의 코지 방향과 충돌할 가능성이 높다.

## 6. Pre-production Decision Order

다음 순서로 기획 결정을 내린다.

1. **게임 정체성 / 플레이어 판타지**
2. **Core Loop**
3. **세션과 장기 성장 구조**
4. **승객·노선·교통 핵심 규칙**
5. **경제와 progression**
6. **UI/UX 및 모바일 조작**
7. **실제 지도 생성 규격**
8. **아트 생성 규칙**
9. **모딩 / Workshop**
10. **수익화 및 출시 플랫폼**
11. **MVP / Vertical Slice 범위**
12. **기술 설계 및 실제 구현 착수**

---

## 7. 다음 결정

**가장 먼저 결정할 것은 Bus Master가 플레이어에게 매일 어떤 경험을 주는 게임인지이다.**

현재 가장 유력한 가설:

> 플레이어는 자기 동네의 작은 버스망을 만들고, 도시가 살아 움직이는 모습을 편하게 지켜본다. 시간이 지나면 새로운 승객 수요와 병목이 발생하고, 플레이어는 몇 분 동안 노선을 손봐 문제를 해결한다. 잘 운영할수록 더 많은 지역과 차량을 다룰 수 있게 되고, 자신의 동네가 점점 대중교통이 편리한 도시로 변한다.

이 가설을 다음 기획 단계에서 검토하고 확정한다.
